# докчек — frontend v1.1

Фронтенд на React, TypeScript и Vite. Кнопка «Проверить» отправляет один документ через `POST /api/v1/checks`, `FormData`, поле `file`. После `202` фронтенд опрашивает статус по `checkId`, при `completed` запрашивает отчёт и показывает замечания по файлу. При сбое пользователь может повторить попытку.

Кнопка «Пример отчёта» открывает отдельный демонстрационный экран. Для настоящего отчёта нужен бэкенд с обработкой DOCX и маршрутами статуса и результата. Заглушка поддерживает только отправку файла.

## Запуск с локальным API

Для запуска приложения и встроенных TypeScript-тестов используйте Node.js 24 или новее. Из корня репозитория в первом PowerShell установите зависимости в подготовленное виртуальное окружение и запустите Flask:

```powershell
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
.\.venv\Scripts\python.exe -m flask --app backend.http run --host 127.0.0.1 --port 8000
```

Во втором PowerShell из корня репозитория:

```powershell
cd frontend
npm.cmd ci
npm.cmd run dev
```

Откройте адрес, напечатанный Vite. Приложение запускается через сервер, а не открытием `index.html` как файла.

В режиме разработки Vite перенаправляет `/api` на `http://127.0.0.1:8000`. Запустите backend отдельно по его инструкции. Если он слушает другой адрес, скопируйте `.env.example` в `.env.local`, измените `API_PROXY_TARGET` и перезапустите Vite:

```dotenv
API_PROXY_TARGET=http://127.0.0.1:8000
```

Значение используется только локальным прокси. Передача файла начинается после «Проверить». Для локальной проверки авторизация пока не требуется.

## Запуск с заглушкой

Пока реальный endpoint в работе, в другом терминале из `frontend`:

```powershell
npm.cmd run mock:api
```

Заглушка слушает `127.0.0.1:8000`, отвечает по контракту и не сохраняет файлы:

| Запрос                                            | Ответ                                             |
| ------------------------------------------------- | ------------------------------------------------- |
| Один файл с расширением `.docx`                   | `202`, `checkId`, `status: queued`                |
| `.txt` или другое расширение                      | `415 UNSUPPORTED_FILE_FORMAT`, понятное сообщение |
| Нет поля `file`                                   | `400 FILE_REQUIRED`                               |
| Неправильный multipart или несколько полей `file` | `400 INVALID_REQUEST`                             |
| Тело запроса больше лимита заглушки               | `413 FILE_TOO_LARGE`                              |

Это проверка интерфейса: заглушка смотрит только на расширение, не проверяет OOXML, повреждение, защиту и содержимое DOCX. Лимит **тела запроса** 10 МиБ, включая multipart, ограничивает только память заглушки и не задаёт лимит продукта. Имена и содержимое файлов не пишутся в логи или на диск. `/health` служит только для проверки доступности заглушки.

Настройки запуска заглушки можно изменить переменными PowerShell:

```powershell
$env:MOCK_DELAY_MS = '2000' # задержка для проверки повторного нажатия; по умолчанию 500
$env:MOCK_PORT = '8000'
$env:MOCK_MAX_BODY_BYTES = '10485760'
npm.cmd run mock:api
```

Изменение `MOCK_PORT` требует такого же порта в `API_PROXY_TARGET`.

## Проверка в браузере

1. Без файла «Проверить» недоступна. Выберите синтетический DOCX; проверьте имя, размер, замену и удаление.
2. Нажмите «Проверить». В Network должен быть один `POST /api/v1/checks` с одним полем `file`, затем запросы статуса и результата. Для `with-heading.docx` отображается ноль замечаний, для `with-bold-text.docx` появляется замечание о заголовке.
3. Отправьте `.txt`: увидите серверную причину отказа. Замените на `.docx` и отправьте снова — должна появиться заявка.
4. Остановите API через `Ctrl+C`, отправьте файл и убедитесь, что ошибка соединения не блокирует следующую попытку. Запустите API и повторите.
5. Отдельная кнопка «Пример отчёта» продолжает открывать демонстрационные замечания; нажатие «Проверить» их не открывает.

Проверку запроса без файла выполняет backend-участник напрямую: интерфейс намеренно не даёт его отправить. Совместный прогон с Дмитрием и ссылки на оба PR нужно зафиксировать после фактической проверки, а не считать выполненными по заглушке.

## Команды и структура

```powershell
npm.cmd test
npm.cmd run build
npm.cmd run preview
```

`build` проверяет TypeScript и создаёт `dist`. `preview` предназначен для локального просмотра сборки; запуск с API описан выше через `dev`. Для размещения frontend и API нужен согласованный серверный маршрут `/api`; эта задача не включает production-конфигурацию.

| Файл                   | Назначение                                                   |
| ---------------------- | ------------------------------------------------------------ |
| `src/App.tsx`          | Выбор файла, текущий статус и отчёт по документу             |
| `src/api/checks.ts`    | Один запрос загрузки и разбор ответов API                    |
| `src/api/results.ts`   | Опрос статуса и загрузка отчёта                              |
| `src/demo.ts`          | Синтетические замечания для отдельной демонстрации           |
| `scripts/mock-api.mjs` | Локальная заглушка, не backend продукта                      |
| `vite.config.ts`       | Прокси локального API                                        |

Визуальное направление сохранено по [Serro](https://serro.ai/): графитовый фон, светлый текст, синий акцент и строгая сетка. Рабочее название «докчек», логотип и тексты оригинальные. Черновик контракта: [ветка develop](https://github.com/Stepik96/ai-documentation-quality-control/blob/develop/docs/developers/mvp-checks-api.md).
