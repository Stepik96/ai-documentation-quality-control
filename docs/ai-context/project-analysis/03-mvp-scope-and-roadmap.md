# 03. MVP, границы и дорожная карта

## 1. Определение MVP

MVP доказывает не «наличие AI», а три критические гипотезы:

1. из неявной практики можно получить согласованный набор проверяемых правил;
2. система находит нарушения с приемлемым числом ложных срабатываний;
3. исправленная копия DOCX сохраняет содержание и поддерживаемое оформление.

## 2. Состав MVP

| Возможность | Приоритет | Комментарий |
|---|---|---|
| Загрузка одного `.docx` | Must | Без пакетной обработки |
| Предварительная проверка файла | Must | Формат, целостность ZIP/OOXML, размер, внешние связи, неподдерживаемые элементы |
| Выбор профиля документа | Must | Руководство пользователя или ЧТЗ; автоопределение может только подсказать |
| Версионированный каталог утверждённых правил | Must | Не хранить единственный источник истины в промпте |
| Проверки структуры и форматирования | Must | Детерминированный слой |
| Ограниченный набор смысловых проверок | Must | Локальная модель, результат с уверенностью и доказательством |
| Отчёт с местом, правилом, тяжестью и предложением | Must | Нужна трассировка к версии правила |
| Исправленная копия с безопасными правками | Must | Исходник неизменяем; смысловые изменения не применять автоматически |
| Статус фоновой обработки и понятные ошибки | Must | Время не гарантировано, поэтому нужен наблюдаемый прогресс |
| Журнал версии правил и движков | Must | Нужен для воспроизводимости и расследования |
| Экспертная оценка на контрольном наборе | Must | Без неё демо не доказывает качество |
| Просмотр и принятие каждой правки в UI | Should | Полезно, но увеличивает объём интерфейса |
| Админ-интерфейс редактирования правил | Should | На первом пилоте каталог может поддерживаться через репозиторий |
| Автоклассификация типа документа | Could | Пользователь обязан подтвердить тип |
| Пакетная загрузка | Could | После одиночного сценария |

## 3. Явно вне MVP

- генерация документа с нуля;
- сверка содержания с кодом, конфигурацией 1С, репозиторием или базой знаний;
- доказательство фактической корректности бизнес-логики;
- PDF, старый `.doc`, ODT, Google Docs и `.docm`;
- Word add-in, интеграции с 1С, ECM, CI/CD и корпоративными порталами;
- преобразование документа в интерактивный сайт;
- обучение собственной фундаментальной модели или обязательный fine-tuning;
- универсальная проверка по всем ГОСТ без выбранного стандарта;
- полноценное визуальное понимание каждого скриншота и проверка его актуальности;
- гарантия корректной обработки макросов, OLE, сложных полей, подписей и всех вариантов Track Changes;
- полностью автономное применение смысловых правок;
- многопользовательские роли, биллинг, внешняя публикация и мобильное приложение.

## 4. Рекомендуемый срез правил

Для пилота следует взять 20–40 утверждённых правил, распределив их так:

- 50–60% — форматирование и структура, проверяемые детерминированно;
- 20–30% — ссылки, подписи, нумерация и согласованность объектов;
- 10–20% — язык и стиль с участием модели.

Количество — рабочая рекомендация, а не условие заказчика. Лучше 20 надёжных правил с тестами, чем 100 расплывчатых.

## 5. Документные профили MVP

1. **Руководство пользователя.** Сильный акцент на пошаговой логике, скриншотах, названиях элементов интерфейса и единообразии терминов.
2. **Частное техническое задание.** Сильный акцент на структуре, нумерации, таблицах, ссылках, объектах системы и ролях.

«Проектное решение» встречалось в обсуждении, но в текущем корпусе нет достаточного отдельного набора для самостоятельного профиля. Его следует добавить позже либо формально объединить с ЧТЗ решением эксперта.

## 6. Диапазон объёма документов

- Функциональный базис пилота: документы 1–50 страниц.
- Файлы до 300 страниц следует принять в технический эксперимент, но не обещать время и полноту до бенчмарка.
- После измерений на целевом оборудовании фиксируются лимиты размера, изображений, страниц и времени.

Это допущение основано на озвученном диапазоне 20–50 и верхней границе около 300 страниц.

## 7. Этапы

| Этап | Результат | Критерий выхода |
|---|---|---|
| 0. Правила | Согласованный каталог v0.1 и тестовые примеры | У каждого правила есть владелец, источник и тест |
| 1. Parser spike | Разбор и обратная сборка DOCX | Контрольные документы открываются без критической потери |
| 2. Детерминированный MVP | Проверки и безопасные исправления | Достигнуты согласованные precision/recall |
| 3. Semantic spike | Локальные языковые проверки | Эксперт оценивает качество по слепому набору |
| 4. Pilot UI | Сквозной веб-сценарий | Автор самостоятельно получает отчёт и результат |
| 5. Пилот | Работа на новых документах | Измерены время, принятие и ошибки; принято решение о развитии |

## 8. Условия остановки или пересмотра

Проект следует сузить или остановить, если:

- эксперт не может согласовать непротиворечивые правила;
- сервис повреждает критичные элементы DOCX при обратной сборке;
- precision низок настолько, что проверка отчёта дольше ручной работы;
- локальная модель не помещается в доступное оборудование или не даёт приемлемого качества;
- невозможно получить новые документы для независимой оценки.

## 9. Ближайший двухнедельный план

1. Назначить владельца Style Guide и провести 2 сессии по 60–90 минут.
2. Утвердить 20–40 правил и два профиля.
3. Получить не менее 10 новых обезличенных документов либо подготовить их под контролем эксперта.
4. Сделать spike сохранности DOCX на самых сложных образцах.
5. Реализовать 5–10 детерминированных правил до подключения LLM.
6. Замерить базовое время ручной проверки.
7. После этого выбрать локальную модель по измерению, а не по популярности.
