# 08. Качество, безопасность и валидация

## 1. Главный принцип оценки

Нельзя оценивать систему на тех же восьми документах, из которых выводились правила. Они подходят для исследования и регрессии, но не для доказательства качества. Нужен независимый набор с разметкой эксперта.

## 2. Наборы данных

| Набор | Назначение | Состав |
|---|---|---|
| Discovery | Вывод кандидатов правил | Текущие 8 документов + замечания |
| Rule fixtures | Юнит-тесты каждого правила | Минимальные DOCX: pass/fail/exception |
| Calibration | Настройка порогов смысловых проверок | Новые размеченные фрагменты |
| Golden holdout | Приёмочная оценка | Новые документы, скрытые от разработчиков до запуска |
| Security corpus | Устойчивость | Повреждённые, чрезмерные, активные и injection-файлы |
| Round-trip corpus | Сохранность Word | Сложные таблицы, секции, поля, рисунки, списки и ссылки |

Для пилота разумно запросить не менее 10–20 новых обезличенных документов. Это рекомендация для разнообразия, не статистическая гарантия.

## 3. Разметка

Единица разметки:

```text
document_id
profile
rule_id + rule_version
location
expected_outcome: pass | violation | exception | unreviewable
severity
safe_fix_expected: yes | no
expert_comment
```

Для смысловых правил часть набора размечают два эксперта независимо. Расхождения показывают предел объективности самого правила; их нельзя автоматически считать ошибкой модели.

## 4. Метрики

### Детекция

- precision, recall и F1 по каждому правилу;
- macro-average по правилам, чтобы частые простые ошибки не скрывали провал редких;
- false positives на документ;
- доля непроверенных элементов;
- стабильность результата при повторном запуске.

### Исправление

- доля корректных safe-auto изменений;
- число незаявленных изменений;
- процент файлов, открывающихся без восстановления;
- сохранность связей, нумерации, рисунков, таблиц и разделов;
- визуальная разница на страницах, которые не должны были меняться.

### Продукт

- медиана ручного времени до/после;
- доля принятых экспертами предложений;
- число возвратов по оформлению;
- доля задач, завершённых полным/частичным/ошибочным результатом.

## 5. Тестовая пирамида

1. **Rule unit tests:** один минимальный DOCX на прохождение, нарушение и исключение.
2. **Parser tests:** корректное чтение наследования стилей, секций, списков и relationships.
3. **Correction tests:** точная OOXML-дельта и повторная валидация.
4. **Contract tests:** строгая схема ответа модели; невалидный ответ не становится находкой.
5. **Integration tests:** полный конвейер от загрузки до выдачи.
6. **Golden regression:** неизменность согласованного набора результатов между релизами.
7. **Security tests:** загрузка, распаковка, prompt injection, доступ, хранение и удаление.
8. **UAT:** эксперт проверяет полезность и доверие, а не только техническое прохождение.

## 6. Проверка сохранности DOCX

Минимальный round-trip checklist:

- открытие в целевой версии Microsoft Word без диалога восстановления;
- сохранение числа секций и их ориентации;
- сохранение headers/footers и разных первых страниц;
- сохранение numbering definitions и ссылок на них;
- сохранение bookmark, hyperlink и relationship;
- сохранение изображений и их размеров;
- сохранение объединений и ширин таблиц;
- сохранение полей и оглавления либо явное предупреждение об их обновлении;
- отсутствие изменений в частях пакета, которые корректор не должен трогать;
- визуальное сравнение страниц вне области исправления.

## 7. Модель угроз

| Угроза | Вектор | Минимальный контроль |
|---|---|---|
| Подмена типа | Файл иного формата с расширением `.docx` | Проверка сигнатуры и Content Types |
| ZIP bomb | Огромная распаковка/много частей | Лимиты распаковки, частей, размера и времени |
| XXE/опасный XML | Внешние сущности | Безопасный XML parser, запрет DTD/externals |
| Внешние relationships | Ссылки на сеть/файлы | Не разрешать, инвентаризировать и предупреждать |
| Макросы/OLE | Активное или встроенное содержимое | Не поддерживать `.docm`; изолировать/блокировать OLE |
| Prompt injection | Текст просит модель игнорировать правила | Разделение данных и инструкций, allowlist задач, schema validation |
| Утечка | API, логи, temp, backup | Локальный inference, редактирование логов, шифрование, retention |
| Межпользовательский доступ | Угадываемый ID результата | Авторизация, непрямые ID, проверка владельца |
| DoS | Большой документ/изображения | Квоты, очередь, timeouts, resource isolation |
| Supply chain | Уязвимая библиотека DOCX/модель | SBOM, фиксация версий, сканирование зависимостей |

## 8. Prompt injection: обязательная политика

Документ всегда является недоверенными данными. Даже фразы вроде «игнорируй предыдущие инструкции» должны анализироваться как содержание, а не исполняться. Контроли:

- модели передаётся узкая задача и только нужный фрагмент;
- применимые правила выбирает код, не документ и не модель;
- ответ допускается только по строгой JSON-схеме с известными `rule_id`;
- любые неизвестные правила и действия отклоняются;
- модель не имеет инструментов записи файлов, сети и изменения каталога;
- коррекция выполняется отдельным детерминированным компонентом;
- injection-набор входит в каждый регрессионный запуск.

## 9. Управление качеством модели

- зафиксировать модель, квантование, runtime, prompt template и параметры;
- калибровать уверенность на реальных данных;
- измерять качество отдельно после каждой замены модели;
- не использовать обратную связь пользователя как автоматический fine-tuning;
- выпускать новую версию только после сравнения с текущей;
- показывать пользователю, какие проверки модель не выполнила.
