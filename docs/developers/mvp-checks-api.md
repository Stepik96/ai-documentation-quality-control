# API проверок документов в MVP

Черновик для согласования с frontend и backend. Описывает три действия: отправить один документ на проверку, узнать статус и получить замечания. Проверка выполняется в фоне.

В локальном сценарии доступны все три маршрута. Вместе с `file` можно передать поле `profile`: `tech-spec` для R02/R03, `user-guide` для R01 или `heading-demo` для тестового правила заголовка. По умолчанию используется `heading-demo`. Отчёт содержит профиль и категорию каждого замечания. `completeness: "complete"` относится к правилам выбранного профиля. Сессии и владение проверкой пока не реализованы. Статус, исходник и результат хранятся до перезапуска Flask.

| Действие | Запрос | Успешный ответ |
| --- | --- | --- |
| Отправить документ на проверку | `POST /api/v1/checks` | `202 Accepted`, идентификатор и статус проверки |
| Узнать статус | `GET /api/v1/checks/{checkId}` | `200 OK`, текущий статус |
| Получить отчёт | `GET /api/v1/checks/{checkId}/result` | `200 OK`, отчёт с замечаниями |

## 1. Отправить документ на проверку

До нажатия «Проверить» пользователь выбирает файл в браузере. По нажатию фронт отправляет `multipart/form-data` с одним полем `file`. Если файл прошёл начальную валидацию, API принимает его, создаёт проверку и возвращает её ID. Фронт блокирует повторное нажатие, пока запрос отправляется. Новая осознанная отправка, например после исправления файла, создаёт отдельную проверку.

Пример запроса для командной строки при наличии тестовой сессии:

```bash
curl -i -X POST "$BASE_URL/api/v1/checks" \
  -b "$SESSION_COOKIE" \
  -F "file=@example.docx"
```

`202 Accepted`

```json
{"checkId":"chk_001","status":"queued"}
```

Пример ошибки: пользователь отправил файл неподдерживаемого формата. Проверка не создаётся, фронт показывает сообщение и предлагает выбрать другой файл.

`415 Unsupported Media Type`

```json
{"error":{"code":"UNSUPPORTED_FILE_FORMAT","message":"Выберите файл поддерживаемого формата."}}
```

Другие ошибки загрузки используют тот же формат: `400 FILE_REQUIRED` при отсутствии файла, `413 FILE_TOO_LARGE` при превышении лимита, `422 INVALID_DOCUMENT` для повреждённого или защищённого файла, если проблема обнаружена до постановки в очередь.

## 2. Узнать статус проверки

Фронт периодически вызывает `GET /api/v1/checks/chk_001` до завершения проверки. Закрытие страницы останавливает опрос со стороны фронта, а обработка продолжается на сервере.

`200 OK`

```json
{"checkId":"chk_001","status":"processing"}
```

| Статус | Что показывает фронт |
| --- | --- |
| `queued` | «Ожидает» |
| `processing` | «Проверяется» |
| `completed` | «Завершено». Можно запросить отчёт |
| `failed` | Сообщение об ошибке. Пользователь может запустить новую проверку |

При `failed` запрос статуса также возвращает `error` с полями `code` и `message`, например `CHECK_FAILED` и «Не удалось проверить документ. Попробуйте ещё раз». При `completed` отчёт уже доступен, в том числе если его удалось составить только частично.

## 3. Получить отчёт

Запрос: `GET /api/v1/checks/chk_001/result`.

`200 OK`

```json
{
  "checkId": "chk_001",
  "rulesVersion": "draft-1",
  "completeness": "partial",
  "summary": {"findingCount": 1},
  "findings": [
    {
      "location": "Абзац 3",
      "ruleId": "EXAMPLE-01",
      "rule": "Заголовок раздела должен иметь стиль «Заголовок 1».",
      "problem": "Для заголовка применён стиль «Обычный».",
      "recommendation": "Примените стиль «Заголовок 1»."
    }
  ],
  "unchecked": ["Не удалось проверить оформление таблиц."]
}
```

Правило в примере условное. Для полного отчёта `completeness` равно `complete`, а `unchecked` пуст. Если замечаний нет, `findings` пуст и `findingCount` равно `0`. Для частичного отчёта фронт показывает непроверенные области даже при нуле замечаний.

До окончания проверки запрос отчёта возвращает `409 CHECK_NOT_READY`. Если проверка завершилась сбоем, возвращается `409 CHECK_FAILED`. Во всех трёх запросах отсутствие активной сессии даёт `401 AUTH_REQUIRED`. Для запроса статуса или отчёта чужой либо неизвестный ID даёт `404 CHECK_NOT_FOUND`.

## Что согласовать перед реализацией

- Поддерживаемые форматы и лимит размера. DOCX использован как пример стартового формата.
- Нужно ли передавать тип документа при отправке для выбора правил.
- Способ передачи сессии и интервал опроса статуса. Cookie в примере иллюстрирует один возможный вариант.
