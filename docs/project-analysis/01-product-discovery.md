# 01. Продукт и результаты исследования

## 1. Проблема

Компания регулярно готовит проектную документацию для заказчиков. Качество сейчас обеспечивает опытный специалист, опирающийся на неформализованные знания. Это создаёт четыре проблемы:

- результат зависит от конкретного эксперта;
- проверка плохо масштабируется и плохо воспроизводится;
- автор узнаёт о части ошибок поздно;
- правила нельзя однозначно тестировать, версионировать и передавать новым сотрудникам.

Нужен сервис, который принимает DOCX, проверяет его по утверждённым правилам, объясняет нарушения и выдаёт безопасно исправленную копию. Сервис помогает эксперту и автору, но на MVP не заменяет экспертное решение в неоднозначных случаях.

## 2. Целевой результат

**Outcome:** сократить ручную рутинную проверку и повысить единообразие документации без потери смысла и повреждения DOCX.

**Продуктовые результаты:**

1. утверждённый человеком Style Guide в человекочитаемом и машиночитаемом виде;
2. сервис проверки двух подтверждённых семейств документов;
3. объяснимый отчёт с точным местом, правилом и предлагаемым исправлением;
4. новая DOCX-копия только с безопасными автоматическими исправлениями;
5. измеримая оценка качества на документах, не использованных для вывода правил.

## 3. Пользователи и заинтересованные стороны

Это не исследованные персоны, а **рабочие роли**, выведенные из процесса. Их нужно проверить интервью.

| Роль | Задача | Боль | Ценность сервиса |
|---|---|---|---|
| Автор документа | Быстро подготовить корректный документ | Не знает всех неявных правил | Ранние и понятные замечания, исправленная копия |
| Эксперт по документации | Подтвердить качество и развивать правила | Повторяющиеся ручные проверки | Фокус на спорных смысловых случаях |
| Руководитель проекта | Сдать заказчику согласованный документ | Переделки и нестабильное качество | Предсказуемый контроль перед выдачей |
| Администратор правил | Обновлять Style Guide без поломки старых проверок | Изменение правил не прослеживается | Версии, тесты, откат и журнал изменений |
| ИБ/инфраструктура | Защитить документы заказчиков | Конфиденциальные данные и вредоносные файлы | Локальная обработка и контролируемый жизненный цикл данных |

## 4. Основные задачи пользователей

- Когда черновик готов, автор хочет получить перечень доказуемых нарушений, чтобы не искать их вручную.
- Когда исправление формальное и однозначное, автор хочет получить исправленную копию без ручной рутины.
- Когда изменение может поменять смысл, эксперт хочет видеть предложение и обоснование, а не скрытую автозамену.
- Когда правило меняется, владелец Style Guide хочет понимать, какие проверки и документы это затронет.

## 5. Ценностная гипотеза

Если проверка будет точной, объяснимой и не будет портить документ, авторы перенесут первичный контроль в сервис, а эксперт будет разбирать только неоднозначные случаи. Ценность разрушается при большом числе ложных замечаний, неясных ссылках на правила или повреждении исходного оформления.

## 6. Пригодность задачи для AI

| Аспект | Оценка | Обоснование |
|---|---|---|
| Повторяемость | Высокая | Многие проверки повторяются от документа к документу |
| Наличие примеров | Средняя | Есть 8 образцов и черновик замечаний, но нет эталонной разметки |
| Необходимость языкового понимания | Высокая | Тональность, тавтология, логические разрывы требуют контекста |
| Ошибкоустойчивость | Средняя | Ложное замечание терпимо, скрытое изменение смысла — нет |
| Детерминируемость | Смешанная | Формат проверяется правилами; смысл — вероятностно |
| Возможность контроля человеком | Высокая | Отчёт и предложения можно подтвердить до применения |

**Вывод:** пригодность высокая для ассистивной проверки, средняя для автономного исправления. Полностью автономный LLM-корректор в MVP не оправдан.

## 7. Критерии успеха

Заказчик не задал численных KPI. Ниже — измерения и предлагаемые стартовые пороги для пилота, которые нужно утвердить.

| Метрика | Как измерять | Предлагаемый порог пилота |
|---|---|---|
| Precision замечаний | Доля подтверждённых экспертом находок | ≥ 95% для детерминированных правил; отдельно по каждому смысловому правилу |
| Recall нарушений | Доля известных нарушений, найденных системой | ≥ 90% для детерминированных правил |
| Безопасность исправлений | Доля автоисправлений без критической регрессии | 100% на контрольном наборе |
| Целостность файла | DOCX открывается и сохраняет поддерживаемые элементы | 100% контрольного набора |
| Принятие рекомендаций | Доля предложений, принятых экспертом | Измерить в пилоте, затем установить порог |
| Экономия времени | Медиана времени проверки до/после | Измерить базовую линию до пилота |
| Производительность | Время по диапазонам страниц и числу объектов | Зафиксировать после бенчмарка на целевом железе |

Порог не следует считать утверждённым требованием до совместной приёмочной сессии.

## 8. Что ещё нужно узнать у пользователей

1. Какие ошибки чаще всего приводят к возврату документа заказчиком?
2. Какие изменения эксперт никогда не разрешит применять автоматически?
3. Как выглядит приемлемая ссылка на место ошибки: страница, заголовок, абзац, объект?
4. Нужен ли автору выбор отдельных исправлений или достаточно отчёта и версии только с безопасными правками?
5. Как часто меняются правила и кто имеет право их утверждать?
6. Какие элементы Word критичны: поля, автособираемое оглавление, комментарии, исправления, OLE, формулы?
